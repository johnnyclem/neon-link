# Concept: MIDI clock path (out and in)

How Link-derived MIDI clock leaves the box, and (new this session) how an
external clock can drive it.

## Clock OUT
- Source of truth is the **Link timeline**. On **link-sync** builds the
  24 PPQN clock is generated by `neon::midi::ClockEngine` inside
  `pulse_task` (core 1, `main/tasks_core1.cpp`), gated on
  `neon_config().midi_clock_out != 0`. It is emitted through the pulse-HW
  gptimer ring → `halesp::midi_uart_send_isr` (direct TX-FIFO write from the
  ISR, `components/neon_hal_esp/src/midi_uart.cpp`).
- **`midi_service` (`main/midi_service.cpp`) is compiled out on link-sync**
  (`#if !CONFIG_NEON_LINKSYNC`); its `esp_timer` `clock_cb` (driver-path
  `midi_uart_send_byte`) is the NON-link-sync path. So P4LCD, Tab5, XIAO,
  EPD, C3, MaTouch all use the pulse_task ISR path — not clock_cb.
- **Gating**: `midi_clock_engine.cpp` only emits `0xF8` while **playing**
  (`if (!playing_ || !have_tl_) return`). Transport stopped ⇒ zero MIDI.
  Start/Stop are `0xFA`/`0xFC`. `midi_nudge_us` shifts the whole stream.
- Enabling clock out on a board = set `kPinMidiTx >= 0`; `pulse_task` inits
  the UART and emits. No service to start.
- Virtual-pulse boards still transmit: `pulse_hw_gptimer.cpp` writes the MIDI
  FIFO regardless of `virtual_`.

## Clock IN / follow (added 2026-08, MaTouch)
- The `MidiRouter` (`midi_router.cpp::on_realtime`) handled Start/Stop but
  **never derived tempo from `0xF8`** — it only forwarded clock. So "follow
  an external MIDI clock's BPM" did not exist.
- MaTouch implementation (`matouch_service.cpp::midi_in_tick`): enable RX
  (`kPinMidiRx=44`), drain `midi_uart_read` each UI frame, count 24 PPQN over
  a ~1 s window → `milli_bpm = clocks * 2.5e9 / dt_us` → push
  `ControlCommand::kSetTempo`; `0xFA/0xFB → kPlayNow`, `0xFC → kStopNow`.
  It's **tempo + transport follow, ~1 BPM / ~1 s resolution — not a PLL.**
- Control commands live in `app_state/timeline_bus.h`
  (`kSetTempo`=5 arg=milli-BPM, `kPlayNow`=3, `kStopNow`=4); the Link service
  (`main/link_service.cpp`) is the only thing that talks to the session.
- A separate, richer **MIDI-PLL** follower exists on `main` (PRs #41–45,
  `ClockSource::kMidiMaster`, `docs/SPIKE_MIDI_PLL.md`) — a true PLL, distinct
  from this coarse UI-task follower.

## The S3 direct-FIFO write — verified, not the bug
`midi_uart_send_isr` uses `WRITE_PERI_REG(UART_FIFO_AHB_REG(UART_NUM_1), b)`.
On the S3 `REG_UART_AHB_BASE(i)` and `REG_UART_BASE(i)` compute the **same**
address (`DR_REG_UART_BASE = 0x60000000`), so the FIFO write is correct on S3
and P4 both. This looked like a suspect during debugging but was a dead end —
see [lessons](../lessons/debugging-lessons.md).

## External MIDI hardware note (M5Stack Unit-MIDI SAM2695)
- Grove port is 5 V; the synth hears the controller's TX on RXD in **both**
  switch modes. The **OUTPUT switch** decides the DIN OUT:
  - **BYPASS**: controller TX → SAM2695 only; DIN IN↔OUT thru → use this to
    take an external clock **into** the board (unit TXD → GPIO44).
  - **SEPARATE**: controller TX → SAM2695 **and** DIN OUT → use this to send
    the board's clock **out** to gear (GPIO43 → unit RXD → DIN OUT).
- MIDI DIN OUT is a ~5 V current loop; underpowering the unit at 3.3 V can
  leave the OUT too weak to trigger a receiver's opto even though its LED
  lights.
